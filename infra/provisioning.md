## One-time key preparation

The private half goes only to the personal credential store and GitHub repository secret `INFERENCE_SSH_KEY`; it does not belong in cloud-init or this repository. When the server order is ready, this local preparation creates the key outside the repository:


## Cloud-init template

Use this only after the reviewed infrastructure code is pushed. Replace both placeholders: `INFRA_COMMIT_SHA` must be an exact 40-character commit containing these scripts; `PUBLIC_DEPLOY_KEY` is the new `.pub` file, never its private half. The order should attach the owner's existing personal admin SSH key through Hetzner's normal SSH-key selection.

```yaml
#cloud-config
package_update: true
packages:
  - ca-certificates
  - curl
write_files:
  - path: /root/priest-ci.pub
    owner: root:root
    permissions: '0600'
    content: |
      PUBLIC_DEPLOY_KEY
  - path: /root/priest-bootstrap.sh
    owner: root:root
    permissions: '0700'
    content: |
      #!/usr/bin/env bash
      set -euo pipefail
      revision=INFRA_COMMIT_SHA
      [[ $revision =~ ^[0-9a-f]{40}$ ]] || exit 1
      mkdir -p /root/priest-bootstrap
      for name in bootstrap-origin.sh ssh-command.sh deploy-origin.sh; do
        curl --fail --silent --show-error --location \
          "https://raw.githubusercontent.com/Twixes/thispriestdoesnotexist/$revision/infra/$name" \
          --output "/root/priest-bootstrap/$name"
      done
      ORIGIN_HOSTNAME=inference.thispriestdoesnotexist.com \
        DEPLOY_PUBLIC_KEY_FILE=/root/priest-ci.pub \
        bash /root/priest-bootstrap/bootstrap-origin.sh
runcmd:
  - [bash, /root/priest-bootstrap.sh]
```

This installs OS/runtime and restricted CI access only. It does not start an application container or deploy a model. After provisioning, verify the SSH host key through the provider console/admin channel, set `INFERENCE_HOST` and `INFERENCE_HOST_KEY` repository variables, provision the runtime token privately, and let the `master` push trigger the first application release.

## Runtime token through Cloudflare CI

Installed Wrangler 4.135.0 supports `wrangler deploy --secrets-file <path>`. Local CLI help and source confirm JSON or `.env` input is converted to `secret_text` bindings during the same Worker upload and omitted existing secrets are retained. The separate `versions secret bulk` command creates a new undeployed version, but it is unnecessary for this project's CI flow. [Cloudflare's secrets documentation](https://developers.cloudflare.com/workers/configuration/secrets/) confirms both behaviors.

Use one randomly generated `INFERENCE_TOKEN` for the origin's root-only `/etc/priest/runtime.env` and Cloudflare's **build secret**. Build secrets are available to build commands; they are distinct from Worker runtime bindings. [Workers Builds configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/)

Once the backend is ready and the Worker proxy is implemented, the CI deploy script can turn that build secret into the runtime secret as part of its normal deployment:

```sh
set -euo pipefail
: "${INFERENCE_TOKEN:?Configure the personal Worker build secret}"
secret_file=$(mktemp)
trap 'rm -f "$secret_file"' EXIT
chmod 600 "$secret_file"
SECRET_FILE="$secret_file" node --input-type=module <<'JS'
import { writeFileSync } from 'node:fs';
writeFileSync(process.env.SECRET_FILE,
  JSON.stringify({ INFERENCE_TOKEN: process.env.INFERENCE_TOKEN }),
  { mode: 0o600 });
JS
npm run deploy -- --secrets-file "$secret_file"
```

Run this exclusively in Cloudflare Workers Builds, not from the laptop. Never echo the token, use shell tracing, commit the temporary file, or use a plaintext Wrangler `vars` entry for it. Use a nonsecret `INFERENCE_ORIGIN` URL in configuration. Configuring a build secret prepares CI; the actual Worker runtime change remains a versioned CI deployment from `master`.

No Cloudflare secret values or auth tokens were accessed to verify this mechanism. No deployment or secret update was performed.
