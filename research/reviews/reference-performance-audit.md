# Reference MPS performance audit

**Benchmark deferred statistics transfers first; then remove unused real-image staging in G phases.** Both are concrete adapter/loop overheads that can be investigated without changing the loss recipe. Their speed impact is unmeasured. Existing evidence does not justify dropping PL/R1, changing the accumulation rule, or promising a large speedup.

Read-only audit of trainer `00b5266875dbe07169025eb7b38b22a412230019c52d1bae77eeb8daf0045b13`, its pinned NVIDIA dependencies, `reference256-paper-b64/config.json`, and saved metrics. No training, profiler job, source edit, job interruption or commit was performed.

## Verified findings

Steps 17–32 processed 1,024 real-image presentations in **585.606 s**. Recomputing from saved records gives Gmain **120.448 s**, Greg **156.067 s**, Dmain **168.985 s**, Dreg **133.938 s**, and **6.169 s** outside recorded phases. PL+R1 account for roughly half the cycle, not all of it. The 6.62-day/million projection describes this concurrent-CDC observation, not an isolated-machine guarantee. Phase timers are ordinary host timers without synchronization at every boundary; they are useful broad accounting, not kernel-exclusive measurements.

The active run has `verify_updates=false`, checkpoint/snapshot interval 125, and no checkpoint or preview in this cycle. Removing smoke assertions or snapshot generation cannot explain or fix these particular timings. PNG decoding, outer-loop EMA, scalar logging and other non-phase work together occupy only about 1% of the measured window, subject to asynchronous attribution.

**1. Statistics are transferred too frequently by our adapter.** `trainer.py:193–195` calls `value.detach().cpu()` on every upstream report before CPU float64 accumulation. At eight microbatches, the unchanged loss emits 24 reports per Gmain phase, 16 per Greg, 40 per Dmain and 32 per Dreg. A 16-step cycle therefore makes **1,120 small MPS-to-CPU transfers**: 384+64+640+32. These introduce host/device rendezvous throughout forward/backward scheduling. Their individual latency and share of the cycle are not measured. CPU float64 statistics are necessary; transferring each small vector immediately is not necessary for the objective. [Pinned upstream report sites](https://github.com/NVlabs/stylegan2-ada-pytorch/blob/main/training/loss.py), [MPS float64 limitation](https://docs.pytorch.org/docs/main/notes/mps.html#double-precision-types).

A candidate adapter could retain detached raw vectors on MPS, pack/copy them once per global step, and replay the original CPU report calls in order **before ADA/metrics/checkpoint consumption**. Preserve CPU reductions rather than replacing them with GPU reductions, retain every ADA real-sign observation, and empty the queue before checkpointing. This is a hypothesis for reducing synchronization with identical statistics semantics, not a tested patch.

**2. G phases stage real images they do not use.** `trainer.py:288–294` transfers and normalizes real pixels on every phase/microbatch. Upstream Gmain/Greg never read `real_img` or `real_c`. Across this cycle, that means **160 unnecessary microbatch transfers/normalizations** (128 Gmain + 32 Greg). Conditional staging for D phases can remove this work without consuming different RNG or changing generated inputs. A later variant could normalize/reuse the same real minibatch for Dmain/Dreg; at 256px a whole 64-image RGB FP32 batch is 48 MiB, but preserve CPU staging at larger resolutions. Measure separately from the statistics change.

**3. The MPS path lacks NVIDIA's specialized CUDA kernels.** `upfirdn2d`, bias/activation and conv-gradient wrappers explicitly select custom kernels only on CUDA; MPS executes their standard-PyTorch reference paths. This is verified implementation selection, **not evidence that those operations run on CPU**. The `grid_sample_gradfix` warning likewise means fallback to PyTorch's grid sampler, whose MPS double backward already passed our tests. Existing artifacts do not provide an operator-level Metal trace identifying which convolution/resampling/backward consumes the time. [Upstream operations](https://github.com/NVlabs/stylegan2-ada-pytorch/tree/main/torch_utils/ops).

**4. Low augmentation probability does not skip geometric machinery.** In this cycle p was approximately .00512–.0128. With bgc flags enabled, the implementation still constructs transforms and enters filtered resampling via the `G_inv is not I_3` object-identity branch; padding also uses device scalar values. That creates plausible synchronization/resampling cost, especially through R1. **Do not simply bypass identity/p=0 augmentation:** it would skip RNG draws and potentially change filtering/numerics. A faithful fast path requires pixel, gradient, second-derivative and RNG equivalence, not just an identity-looking transform matrix. [Upstream augmentation](https://github.com/NVlabs/stylegan2-ada-pytorch/blob/main/training/augment.py).

## Hypotheses and lower priorities

Concurrent CDC may materially slow the run, but these logs do not quantify contention. Compare later when normal experiment scheduling permits; this audit does not recommend interrupting active jobs. CPU uint8 caching could avoid repeated decode of 110 originals (about 20.6 MiB at 256px), but current accounting makes it a lower priority than in-phase work. Replacing per-tensor Adam/EMA operations or fused-modconv selection also needs profiling and gradient checks first.

Do not treat allocator tuning, mixed precision or compiler flags as proven free speed. PyTorch documents `PYTORCH_MPS_PREFER_METAL` as applying to **matmul**, while `FAST_MATH` changes numerical behavior. Neither addresses a demonstrated bottleneck here. Changes to microbatch size can alter accumulation/PL updates and minibatch statistics; preserve batch64/micro8 for the first comparison. [Official MPS environment variables](https://docs.pytorch.org/docs/2.14/mps_environment_variables.html).

## Proposed bounded next measurement

Use an isolated copy of one saved checkpoint, fixed inputs and RNG, with no optimizer updates. Profile one microbatch8 pass through each actual phase (PL uses four examples), with MPS signposts and synchronization only around measured regions. Use `torch.mps.profiler.profile(wait_until_completed=False)`; enabling per-operation waiting distorts performance. Capture CPU copy/wait activity and Metal convolution, resampling and double-backward work. [Official profiler](https://docs.pytorch.org/docs/2.14/generated/torch.mps.profiler.profile.html), [synchronization](https://docs.pytorch.org/docs/2.14/generated/torch.mps.synchronize.html).

Then A/B only the deferred-statistics adapter from the same state, followed separately by G-phase staging removal. Require identical RNG consumption, matching PL mean/ADA statistics, finite matching gradients in all four phases, and the existing exact CPU checkpoint-continuation regression. Keep concurrency conditions recorded and stable. Only a measured improvement should earn a full 16-step comparison; no active trainer should change during this investigation.
